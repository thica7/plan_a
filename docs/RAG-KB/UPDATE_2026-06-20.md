# RAG KB 链路优化更新说明

日期：2026-06-20
分支：`rag-kb-optimize`

## 更新背景

本轮重点是把原本偏独立运行的 RAG KB crawler、collector、writer 与质量门禁串成一条可追踪的证据链，降低报告阶段出现信息不准确、过期、冲突或裸 RAG 文本绕过证据校验的风险。

核心原则：

1. KB 不是最终事实，只能作为候选证据。
2. collector 必须负责验证、过滤、补新，并统一沉淀为 `RawSource`。
3. writer 只能使用 `RawSource` 与 `[source:...]` token，不能直接消费裸 RAG hit。
4. quality gate 要能拦截过期 KB、KB/live 冲突、弱来源和引用缺失。
5. KB 回写必须有污染防护，避免把旧 KB 复用结果再次写回 KB。

## 已完成改动

### 1. Collector 接入 KB warm-start

collector 在真实采集前会先尝试从 RAG KB 召回候选证据：

1. 使用 `rag_retrieve_tool` 做 KB 检索。
2. 默认使用 `mode="sparse"`，避免本地没有向量库或 embedding 服务时阻塞采集主流程。
3. 将 KB hit 转成 `RawSource(candidate_origin="rag_kb")`。
4. 继续走 collector 的来源质量检查，KB 命中不会被直接当成事实。

收益：

1. crawler/KB 的历史资料能够进入 collector 主证据链。
2. collector 可以减少重复抓取，并优先基于已有资料做验证。
3. KB 来源在 trace/source metadata 中可见，后续能倒查来源。

### 2. 修复 collect_join 到 KB 的回写

原先 collect_join 里有一段自动入库逻辑，但它访问了不存在的 `source.text/source.ok` 字段，异常又被吞掉，因此回写实际不可靠。

本轮改为显式 `_sync_collected_sources_to_kb`：

1. 只回写验证过、有 URL、高置信、质量通过的来源。
2. 跳过 `candidate_origin="rag_kb"` 的复用来源，避免循环污染。
3. 跳过低置信、失败、无 URL、文本过短、source type 不在白名单的来源。
4. 写入 metadata：`run_id`、`raw_source_id`、`crawl_run_id`、`collector_confidence`、`candidate_origin`、`fetch_method`。
5. 默认 `index_vectors=False`，先保证 SQLite/FTS 稀疏检索链路稳定。

收益：

1. collector 采集结果可以反哺 KB。
2. 回写来源可追踪，后续支持污染定位与回滚。
3. 不会把 KB 复用结果再次写回造成自我强化。

### 3. RAG 检索新增 sparse-only 模式

新增能力：

1. `RetrievalRequest.mode` 支持 `sparse`。
2. `RetrievalService` 支持仅走 SQLite/FTS 检索。
3. `rag_retrieve_tool` 支持 `mode` 和 `preset` 参数。
4. `RetrievalHit` 补充 `fetched_at`、`last_seen_at`、`status`，为 freshness gate 提供线索。

收益：

1. 没有 Qdrant 或 embedding 的环境下，collector 仍能使用 KB。
2. 本地开发、CI 与轻量部署不再被向量索引强绑定。
3. pricing、plan name、security feature 这类关键词型事实可以先通过 sparse 检索兜底。

### 4. Writer 边界收紧

移除了 writer grounding 阶段直接追加裸 RAG dict 的逻辑。

现在 writer 只会看到：

1. `RawSource` 摘要。
2. 已存在的 `[source:...]` token。
3. KB reused source 的 token 提示。

收益：

1. writer 不能绕过 collector/QA 使用未验证 RAG 文本。
2. 报告里的 KB 证据仍然有 source id，可被质量门禁追踪。
3. 降低“RAG 命中看起来像事实，但没有进入证据账本”的失真风险。

### 5. Quality gate 增加 KB freshness 与 contradiction 检查

新增 collector 侧检查：

1. freshness gate：
   - pricing 默认 45 天。
   - security/compliance/privacy/procurement 默认 90 天。
   - feature/api/docs/model/integration 默认 120 天。
   - persona/user/customer/review/community 默认 180 天。
   - KB 复用来源缺少观察日期时给 warning。
   - real run 中过期来源生成 collector blocker redo。

2. contradiction gate：
   - 检查同一 competitor/dimension 下 KB reused source 与 live source 的互斥声明。
   - 覆盖 SSO/SAML/SCIM/SOC 2/API/free plan/enterprise plan/self-hosted 等高风险事实项。
   - pricing 下检查同一 plan/cadence 的价格冲突。
   - 冲突时不让 writer 直接选边站，而是生成 consistency blocker，交给 collector 重新验证。

收益：

1. 可拦截旧 KB 与新网页冲突。
2. 可拦截过期 pricing/security/feature 证据。
3. 质量门禁能把问题指回 collector redo，而不是在报告阶段静默失真。

### 6. 前端与类型同步

同步内容：

1. 重新导出 OpenAPI。
2. 更新前端生成类型。
3. 手写 `RawSource` 类型补齐 `candidate_origin`、`candidate_rank`、`candidate_confidence`、`fetch_method`、`quality_score`、`failure_reason`、`metadata`。
4. 搜索页支持 dense weight 为 0 时发送 `mode="sparse"`。
5. 搜索页展示 KB 的 `fetched_at`、`last_seen_at`、`status`。

收益：

1. 前端可以展示 KB 复用来源。
2. 减少后端 schema 与前端手写 DTO 漂移。
3. sparse 检索能力可以在 UI 中被实际使用。

补充打通：

1. `buildReportSourceBundle` 已识别 `kb_raw_source_id`，并将其加入 source alias，避免 KB 同步后的 enterprise evidence 丢失原始 collector RawSource 引用。
2. `kb_collector_candidate_origin`、`kb_collector_fetch_method`、`kb_collector_confidence` 会映射回报告侧 `RawSource`，source trace 可以继续呈现 collector provenance。
3. 新增 `sourceBundle.test.ts` 覆盖 KB provenance 从 enterprise evidence metadata 到报告 source bundle 的传递。

### 7. 新增 RAG KB 质量验收集

新增 `eval/rag-kb-quality-gate-eval.jsonl`，覆盖 7 类高风险场景：

1. pricing 变更。
2. 功能下线。
3. 官网与第三方来源冲突。
4. 旧 KB 文档与新网页资料冲突。
5. 竞品名称歧义。
6. security/SOC2/SCIM 冲突。
7. free plan 冲突。

新增 `backend/tests/unit/test_rag_kb_eval_set.py`，保证 eval set 结构稳定、场景覆盖完整、证据可追踪、KB/live 来源组合存在、预期 gate 明确。

同时 `.github/workflows/quality.yml` 新增 RAG KB targeted quality tests，避免依赖一次性跑完整 backend unit。

### 8. KB 到 Enterprise Evidence 审计字段透传

继续打通 KB 到企业证据链路：`sync_knowledge_to_evidence` 在把 KB document 投影为 `EvidenceRecord` 时，会保留更多审计字段。

新增透传字段包括：

1. `kb_document_status`、`kb_document_version`、`kb_document_source_type`。
2. `kb_fetched_at`、`kb_indexed_at`、`kb_last_seen_at`、`kb_freshness_basis_at`、`kb_freshness_score`。
3. `kb_raw_source_id`、`kb_collector_run_id`、`kb_collector_candidate_origin`、`kb_collector_fetch_method`、`kb_collector_confidence`。
4. evidence sync state 中记录 `evidence_raw_source_id`、`kb_raw_source_id`、`kb_document_status` 等水位审计字段。

收益：

1. collector verified source 回写 KB 后，再经 `kb-sync` 进入 enterprise evidence 时不会丢失原始 `RawSource` 线索。
2. enterprise search、gap fill、release gate 和前端可以解释证据来自哪次 collector 回写、哪个 KB 文档版本，以及新鲜度依据是什么。
3. RAG KB quality CI 现在覆盖 `test_knowledge_evidence_bridge.py`，防止这条桥接链路后续退化。

## 当前链路状态

当前已形成的主链路：

```text
KB crawler / batch ingest
  -> KnowledgeRepository documents/chunks
  -> rag_retrieve_tool(mode="sparse")
  -> collector KB warm-start
  -> RawSource(candidate_origin="rag_kb")
  -> collector live verification / QA freshness / contradiction gate
  -> writer only uses source tokens
  -> collect_join verified sources write back to KB
```

并行存在的企业证据链路：

```text
KnowledgeRepository documents
  -> enterprise kb-sync
  -> EvidenceRecord(metadata 保留 KB/collector 审计字段)
  -> enterprise search / release gate / gap fill
```

这两条链路职责不同：

1. collector 链路负责本次 run 的证据采集、验证、报告 grounding。
2. enterprise kb-sync 链路负责把 KB 投影成项目级 EvidenceRecord，服务企业搜索、release gate 与 gap fill。

## 仍需继续打通的问题

### P0：KB 文档版本化与污染回滚

目前回写 metadata 已经包含 `run_id/raw_source_id/crawl_run_id`，但还需要进一步把同 URL 多次采集的版本关系显式化：

1. 保留每次采集版本。
2. 支持按 `crawl_run_id` 或 `raw_source_id` 定位污染来源。
3. 支持回滚某次 collect_join 写入。

### P0：前端可解释性面板

当前后端 trace/source metadata 已经具备信息，但前端还没有完整展示：

1. KB warm-start query。
2. accepted/rejected KB hits。
3. rejected reason。
4. KB document/chunk/source id。
5. freshness/contradiction gate 指向的证据对。

### P1：freshness schema 结构化

建议将 `observed_at`、`last_verified_at`、`expires_at`、`freshness_score` 结构化到 KB document/source metadata 中，并按 dimension/source_type 自动计算过期策略。

### P1：contradiction 从启发式升级为结构化 claim validator

当前 contradiction gate 已能兜住常见互斥事实，但仍是启发式。后续建议：

1. 从 source snippet 中抽取结构化 claim。
2. 给 claim 标注 subject、predicate、value、time、source authority。
3. 将冲突落为 `conflict_evidence`，供 QA、前端、redo 直接消费。

### P1：CI 测试分片

当前完整 backend unit 在本地环境曾出现 exit 137。建议继续把质量门禁拆成更明确的 shards：

1. `rag-kb-quality`。
2. `business-intel-quality`。
3. `agent-run-service`。
4. `knowledge-routes`。
5. `frontend-contract`。

## 结论

本轮已经把 RAG KB 从“独立知识库/爬虫能力”推进到“collector 可复用、writer 不绕过、quality gate 可拦截、verified source 可回写”的闭环雏形。

下一步应该继续补齐可解释性、版本化和结构化冲突检测，让 KB 不只是能参与流程，而是能被审计、回滚、解释和稳定验收。
