# RAG KB 链路优化更新说明

日期：2026-06-20
分支：`rag-kb-optimize`

## 目标

本轮目标是把原本偏独立的 RAG KB crawler、collector、writer 和质量门禁串成一条可追踪、可验收、可回滚的证据链，降低报告阶段出现信息不准确、过期、冲突或 RAG 文本绕过证据校验的风险。

核心原则：

1. KB 不是最终事实，只能作为 collector 的候选证据来源。
2. collector 必须统一负责验证、过滤、补新，并把证据沉淀为 `RawSource`。
3. writer 只能通过 `RawSource` 和 `[source:...]` token 使用证据，不能直接消费裸 RAG hit。
4. quality gate 必须能拦截过期 KB、KB/live 冲突、弱来源和引用缺失。
5. collector 回写 KB 必须可定位、可审计、可回滚，避免循环污染。

## 已完成改动

### 1. Collector 接入 KB warm-start

collector 在真实采集前会优先尝试从 RAG KB 召回候选证据：

1. 使用 `rag_retrieve_tool` 查询 KB。
2. 默认使用 `mode="sparse"`，避免本地没有向量库或 embedding 服务时阻塞采集主流程。
3. 将 KB hit 转成 `RawSource(candidate_origin="rag_kb")`。
4. 继续经过 collector 的来源质量检查、freshness 检查和 contradiction 检查。

收益：crawler/KB 的历史资料现在能进入 collector 主证据链，而不是只停留在独立知识库中。

### 2. 修复 collect_join 到 KB 的回写

原先 collect_join 中的自动入库逻辑访问了不存在的 `source.text/source.ok` 字段，异常又被吞掉，因此 collector 证据并没有可靠沉淀进 KB。

现在改为显式 `_sync_collected_sources_to_kb`：

1. 只回写 verified、有 URL、高置信、质量通过的来源。
2. 跳过 `candidate_origin="rag_kb"` 的复用来源，避免 KB 自我强化污染。
3. 跳过低置信、失败、无 URL、文本太短、类型不在白名单的来源。
4. 写入 `run_id/raw_source_id/crawl_run_id/collector_confidence/candidate_origin/fetch_method` 等 metadata。
5. 默认 `index_vectors=False`，先保证 SQLite/FTS sparse 检索链路稳定。

### 3. RAG 检索支持 sparse-only 模式

新增能力：

1. `RetrievalRequest.mode` 支持 `sparse`。
2. `RetrievalService` 支持只走 SQLite/FTS。
3. `rag_retrieve_tool` 支持 `mode` 和 `preset` 参数。
4. `RetrievalHit` 返回 `fetched_at/last_seen_at/status`，供 freshness gate 使用。

收益：没有 Qdrant 或 embedding 的轻量环境也能使用 KB，特别适合 pricing、plan name、security feature 等关键词型事实兜底。

### 4. Writer 边界收紧

移除了 writer grounding 阶段直接追加裸 RAG dict 的逻辑。

现在 writer 只能看到：

1. `RawSource` 摘要。
2. 已存在的 `[source:...]` token。
3. KB reused source 的 token 提示。

收益：writer 不能绕过 collector/QA 使用未验证 RAG 文本，报告里的 KB 证据仍然可追踪到 source id。

### 5. Quality gate 增加 KB freshness 与 KB/live contradiction 检查

collector QA 新增检查：

1. freshness gate：pricing 45 天、security/compliance/privacy/procurement 90 天、feature/api/docs/model/integration 120 天、persona/user/customer/review/community 180 天。
2. KB 复用来源缺少原始观察时间时给出 warning。
3. real run 中过期来源会生成 collector blocker redo。
4. contradiction gate 会检查同一 competitor/dimension 下 KB reused source 与 live source 的冲突。
5. 覆盖 SSO/SAML/SCIM/SOC 2/API/free plan/enterprise plan/self-hosted 以及 pricing plan price mismatch。

### 6. KB 到 Enterprise Evidence 的审计字段透传

`sync_knowledge_to_evidence` 将 KB document 投影为 `EvidenceRecord` 时，会保留：

1. `kb_document_status/kb_document_version/kb_document_source_type`。
2. `kb_fetched_at/kb_indexed_at/kb_last_seen_at/kb_freshness_basis_at/kb_freshness_score`。
3. `kb_raw_source_id/kb_collector_run_id/kb_collector_candidate_origin/kb_collector_fetch_method/kb_collector_confidence`。
4. sync state 中记录 `evidence_raw_source_id/kb_raw_source_id/kb_document_status` 等水位字段。

收益：collector verified source 回写 KB 后，再经 `kb-sync` 进入 enterprise evidence 时不会丢失原始 `RawSource` 线索。

### 7. RAG sparse hit 保留 collector 原始审计字段

修复一个隐藏断点：`RetrievalHit` 原来没有 `metadata`，sparse/dense 检索返回 KB hit 时只带 `document_id/chunk_id/status/fetched_at`，collector warm-start 无法从 hit 继续追到原始 `raw_source_id/run_id/collector_*`。

现在：

1. `RetrievalHit` 增加 `metadata` 字段。
2. sparse 检索从 `KnowledgeDocument.metadata` 透传审计字段。
3. dense 检索在回查 SQLite document status 时同步回填 document metadata。
4. collector `RawSource(candidate_origin="rag_kb")` 会映射 `kb_raw_source_id/kb_collector_run_id/kb_collector_candidate_origin/kb_collector_fetch_method/kb_collector_confidence`。

新增测试：`backend/tests/unit/test_rag_kb_collector_chain.py`，用临时 SQLite 验证 `ingest_document_tool(index_vectors=False)` 写入的 verified source 可以经 `rag_retrieve_tool(mode="sparse")` 被 collector warm-start 复用，并保留原始 collector 审计字段。

### 8. 前端 report source trace 展示 KB 审计信息

报告侧 `ReportSourceTrace` 现在会在每张 source card 中展示紧凑审计字段：

1. `Origin`：是否为 KB reused。
2. `Fetch` 与 `Candidate`：collector/enterprise projection 的来源与置信度。
3. `KB status` 与 `KB document`：KB 文档状态和版本。
4. `KB raw source` 与 `Collector run`：回到原始 collector 证据与 run。
5. `Fetched/Last seen/Freshness`：新鲜度依据。

新增 `ReportSourceTrace.test.tsx`，验证 KB metadata 从 enterprise evidence/source bundle 进入报告 source trace 后，用户可见、可定位。
### 9. 前端 report source bundle 识别 KB provenance

`buildReportSourceBundle` 已识别：

1. `kb_raw_source_id`，并加入 source alias。
2. `kb_collector_candidate_origin/kb_collector_fetch_method/kb_collector_confidence`。
3. `metadata.kb_sync`，用于兜底识别 `candidate_origin="rag_kb"`。

收益：enterprise evidence metadata 可以继续映射回报告侧 source bundle，降低引用断链风险。

### 10. 新增 RAG KB 质量验收集

新增 `eval/rag-kb-quality-gate-eval.jsonl` 和 `backend/tests/unit/test_rag_kb_eval_set.py`，覆盖：

1. pricing 变更。
2. 功能下线。
3. 官网与第三方来源冲突。
4. 旧 KB 与新网页资料冲突。
5. 竞品名称歧义。
6. security/SOC2/SCIM 冲突。
7. free plan 冲突。
8. privacy/customer-data training policy 冲突。
9. data retention window 冲突。

### 11. 新增 KB 污染回滚能力

新增 `KnowledgeRepository.rollback_documents` 和 `POST /knowledge/documents/rollback`。

支持按以下 selector 定位污染写入：

1. `document_ids`
2. `run_id`
3. `raw_source_id`
4. `crawl_run_id`

行为：

1. 将匹配的 active/stale 文档置为 `archived`。
2. 默认恢复同 `canonical_url` 的上一个 archived 版本为 active。
3. API 层会删除被归档文档的 Qdrant 向量，避免 dense/hybrid 检索继续召回污染内容；如果外部 Qdrant 清理失败，会在 `vector_cleanup_error` 中返回，SQLite 回滚结果仍然可见。
4. 返回 `matched_count/rolled_back_count/restored_count/archived_document_ids/restored_document_ids/skipped_document_ids`。

新增测试：`backend/tests/unit/test_knowledge_rollback.py`。

### 12. 前端 KnowledgePage 增加 KB rollback 操作入口

`KnowledgePage` 现在可以直接执行污染回滚：

1. 支持按 `run_id/raw_source_id/crawl_run_id` 输入 selector 触发 rollback。
2. 支持在文档详情弹窗里按单个 `document_id` 回滚。
3. 支持选择是否 `restore_previous`，默认恢复同 canonical URL 的上一个版本。
4. 页面展示 `matched/archived/restored/skipped` 数量、归档/恢复 document id，以及 `vector_cleanup_error`。
5. `knowledgeStore.rollbackDocuments` 会压缩空 selector、调用 `/api/knowledge/documents/rollback`，并在成功后刷新文档列表。

新增测试：`frontend/src/stores/knowledgeStore.test.ts`，验证 rollback payload、列表刷新和空 selector 拦截。

### 13. 新增结构化 source claim 冲突校验

新增 `packages.rag.structured_claims`：

1. 从 `RawSource` 中抽取 `subject/predicate/value/polarity/source_id/is_kb_reuse`。
2. 将 SSO/SAML/SCIM/SOC 2/API/free plan/self-hosted 等二元事实结构化。
3. 将 pricing plan/cadence/amount 结构化为 `price:<plan>:<cadence>`。
4. 将 customer-data/model-training policy 结构化为 `privacy:data_training`。
5. 将 data retention 天数结构化为 `retention:data`。
6. 只在同一事实项同时存在 KB reused 与 live source 且 value/position 冲突时生成 conflict。
7. claim_validator 复用同一结构化 fact position 抽取，报告 claim 与 evidence 之间的 pricing、privacy training、data retention 冲突也会进入 conflicting_evidence。
8. collector QA 继续输出原有 `QCIssue` 格式，redo 流程不变。

新增测试：`backend/tests/unit/test_structured_source_claims.py` 与 `backend/tests/unit/test_business_intel.py::test_claim_validator_detects_structured_pricing_conflict`、`::test_claim_validator_detects_customer_data_training_conflict`、`::test_claim_validator_detects_data_retention_conflict`。

### 14. Claim validation release gate issue 透传 KB 审计 metadata

修复另一个验收视角的断点：claim validator 能识别报告 claim 与 source claim 的结构化冲突，但 release gate 过去只暴露 `evidence_ids/claim_ids`，缺少可直接定位污染来源的 KB 审计线索。

现在：

1. `BusinessQAFinding` 增加 `metadata` 字段。
2. release gate 的 `claim_self_consistency_required` issue 会记录 `claim_validation_issue_types/failed_checkers/conflicting_evidence_ids`。
3. 同一 issue 会带 `evidence_audit_trail`，包括 `evidence_id/raw_source_id/url/title/quality_label/source_type/kb_document_id/kb_document_version/kb_document_status/kb_raw_source_id/kb_collector_run_id/kb_freshness_score`。
4. `quality_findings_from_release_gate` 会继续透传这些 metadata，方便统一质量面板、redo 和人工审计直接定位问题来源。

新增测试：`backend/tests/unit/test_business_intel.py::test_release_gate_claim_conflict_includes_kb_audit_metadata`。

### 15. 前端 release gate issue 展示 KB 审计摘要

`ReportReviewDesk` 的 gate issues 卡片现在会展示 release gate issue metadata 中的 KB 审计摘要：

1. claim validation issue type 与 conflicting evidence id。
2. evidence raw source id。
3. KB document id/version/status。
4. KB raw source id 与 collector run id。
5. freshness score。

收益：质量门禁发现 claim/source 冲突时，前端不再只展示长 message，而是能直接指出问题来自哪个 KB document/version 与原始 collector source。

新增测试：`frontend/src/features/workbench/ReportReviewDesk.test.tsx`。

### 16. CI 按项目验收视角拆分

`.github/workflows/quality.yml` 已拆成：

1. `backend-lint`：后端重点模块 ruff、secret scan 与 OpenAPI JSON 同步检查。
2. `backend-business-quality`：报告质量、claim validation 审计 metadata、LLM client、secret scan、真实 run 质量对比脚本。
3. `backend-knowledge-acceptance`：KB 版本链、回滚、chunk/crawl_run_id 持久化。
4. `backend-rag-kb-quality`：RAG KB eval、bridge、sparse tool-to-collector chain、structured claims、collector KB warm-start/write-back、writer token 边界。
5. `frontend-build`：前端安装、OpenAPI TypeScript 生成物同步检查、report source trace/source bundle/knowledgeStore rollback/release gate issue audit/KB rollback/scoped redo action targeted tests 与 build。

收益：后续 PR 失败能快速定位是业务质量、知识库、RAG KB 链路还是前端构建问题，也降低单个后端 job 过重导致的失败不透明。

### 17. OpenAPI 契约同步防漂移

本轮复查发现后端 `BusinessQAFinding.metadata` 与 KB rollback API 已存在，但 `frontend/openapi.json` 和 `frontend/src/api/openapi.ts` 仍停留在旧 schema。风险是：前端已经开始依赖 release gate issue metadata 展示 KB 审计摘要，但后续重新生成类型时可能丢字段，或者新 rollback API 在契约层不可见。

已处理：

1. 重新从 FastAPI 导出 `frontend/openapi.json`。
2. 重新生成 `frontend/src/api/openapi.ts`。
3. `BusinessQAFinding` 的 OpenAPI schema 现在包含 `metadata`。
4. KB rollback endpoint、`DocumentRollbackRequest`、`KnowledgeRollbackResult` 进入前端 OpenAPI 契约。
5. CI 新增 OpenAPI JSON 同步检查与 TypeScript 生成物同步检查，避免 API/schema 改动只停在后端。

收益：RAG KB 审计 metadata、rollback 能力和前端类型契约形成同源校验，减少“后端已实现但前端契约不可见”的隐性失真。

### 18. Release gate blocker 一键联动 KB rollback

`ReportReviewDesk` 现在会从 release gate issue 的 `evidence_audit_trail` 推导 KB rollback selector，并在 gate issue 卡片里显示 `Rollback KB evidence` 操作。

推导顺序：

1. 优先使用 `kb_document_id`，按 document id 精确回滚污染 KB 文档。
2. 如果没有 document id，则使用 `kb_raw_source_id`。
3. 如果仍没有 raw source id，则使用 `kb_collector_run_id`。
4. rollback 默认 `restore_previous=true`，尽量恢复同 canonical URL 的上一版本。
5. 操作完成后刷新当前 workbench 项目数据，并在 issue 卡片回显 matched/archived/restored 数量。

收益：质量门禁发现 claim/source 冲突后，reviewer 不需要再手工复制 KB document id 到 KnowledgePage；可以直接从 blocker 卡片处理污染 KB 证据，再回到报告/release gate 闭环复查。

新增测试：`frontend/src/features/workbench/ReportReviewDesk.test.tsx` 覆盖 rollback selector 生成与按钮点击 payload。

### 19. Release gate blocker 一键触发 scoped redo

`ReportReviewDesk` 在当前 report version 具备 `run_id` 时，会在 gate issue 卡片里显示 `Redo affected branch` 操作。

行为：

1. 点击后调用现有 `/api/runs/{run_id}/redo`。
2. 后端复用 `_sync_release_gate_repair_issues` 生成的 run-level QA findings 和 redo scopes。
3. `run_scoped_redo` 会选择 pending release gate/QA issue，合并 scope，并路由到 collector/analyst/writer/comparator 等分支。
4. 前端记录 issue id、run id、redo 后 run status，并刷新当前 workbench 项目数据。
5. 没有 `run_id` 的报告版本不会显示 redo 操作，避免出现不可执行按钮。

收益：reviewer 可以在同一张 gate blocker 卡片上先 rollback 污染 KB 证据，再触发受影响分支的 scoped redo，形成“发现冲突 -> 清理 KB -> 重跑分支 -> 复查 release gate”的操作闭环。

新增测试：`frontend/src/features/workbench/ReportReviewDesk.test.tsx` 覆盖 redo 按钮 payload 与 redo feedback。

### 20. Activity 页新增 release gate 人工复核队列

本轮继续补齐第 19 节之后仍偏弱的“人工复核队列”衔接。过去 release gate blocker 的 KB 审计信息和动作主要在 Report Review Desk 内可见；如果 reviewer 进入 Activity 页，只能看到普通通知流和审计日志，缺少按 blocker 组织的待处理任务视角。

已处理：

1. 新增 `frontend/src/features/workbench/releaseGateReview.ts`，集中维护 release gate issue -> audit rows、KB rollback selector、review task 的推导逻辑，避免报告页和活动页各自复制 selector 判断。
2. 新增 `ReleaseGateReviewQueue`，在 Activity 页侧栏展示 release gate review tasks。
3. 每个 task 展示 severity、处理阶段、claim/evidence 数量、rule id、KB document/version/status、KB raw source、collector run、freshness 等审计线索。
4. 当 task 能定位到 KB 污染来源时，Activity 页可直接触发 `Rollback KB`，复用同一套 document_id/raw_source_id/collector_run_id selector。
5. 当当前 report version 有 `run_id` 时，Activity 页可直接触发 `Scoped redo`，与 Report Review Desk 的 redo 行为保持一致；没有 `run_id` 时不展示不可执行动作。
6. Report Review Desk 继续保留原有 gate issue 卡片，但审计与 rollback selector 已改为复用共享 helper。

收益：release gate blocker 不再只散落在报告阅读视图里，而是在 Activity 页形成 reviewer 可扫描、可操作的复核任务队列；RAG KB 污染发现、KB rollback、scoped redo、审计日志/通知流现在处在同一个活动工作台上下文里，离完整人工复核闭环更近一步。

新增测试：`frontend/src/features/workbench/ReleaseGateReviewQueue.test.tsx` 覆盖 review task 推导、KB rollback action、scoped redo action，以及无 `run_id` 时隐藏 redo。

### 21. 报告审批被 release gate 拦截时写入通知链路

补齐 Activity 页复核队列之后，本轮继续检查后端持久化链路：run 完成时已经会写 `release_gate_blocked` 通知，但报告审批工作流里如果 reviewer 点击 approve 后被 release gate 拦截，过去只会抛出异常，通知流不会同步出现新的 blocker 记录。

已处理：

1. `ReportApprovalActivities._enforce_release_gate` 在 gate 不允许审批时，会先写入 `release_gate_blocked` 通知，再抛出原有 blocked approval 异常。
2. 通知使用稳定 id，包含 `report_version_id/run_id/readiness_score/blocker_count/warn_count/issue_count/issues`，Temporal 重试时会 upsert 同一条记录，不会重复生成多条通知。
3. `created_by` 标记为 `report-approval-workflow`，`resource_type/resource_id` 指向被拦截的 report version，方便 Activity 页和审计日志串起来。

收益：release gate blocker 现在不只在 run finalize 阶段可通知；人工审批阶段触发的 blocker 也会进入同一条通知/审计链路，reviewer 能在 Activity 页看到复核任务、通知和审计记录之间的一致证据。

新增测试：`backend/tests/unit/test_temporal_workflows.py::test_report_approval_activities_block_weak_report_version` 覆盖审批被 release gate 拦截后写入 `release_gate_blocked` 通知和 issue metadata。

### 22. 扩大结构化事实校验到 privacy training 与 data retention

针对“信息不准确/失真”里最容易造成高风险误判的一类问题，本轮继续扩大结构化 claim 覆盖面：过去 deterministic fact positions 主要覆盖 pricing、SSO/SAML/SCIM/SOC 2/API/free plan/self-hosted；现在新增隐私训练策略和数据保留期。

已处理：

1. `structured_claims.extract_structured_fact_positions` 新增 `privacy:data_training`，区分 `does_not_train` 与 `trains`。
2. 新增 `retention:data`，识别 30/90 等 day-based retention window。
3. `claim_validator` 将 privacy/customer data/customer code/training/data retention 识别为 high-risk claim。
4. 报告 claim 与 evidence 对这些结构化事实出现不同 position 时，会生成 `conflicting_evidence` blocker。
5. `eval/rag-kb-quality-gate-eval.jsonl` 新增 `privacy_training_conflict` 与 `retention_conflict` 两个验收场景。
6. CI business-quality shard 增加 privacy training conflict 与 data retention conflict 的 claim validator targeted tests。

收益：质量门禁不再只对价格和安全功能做结构化冲突拦截；对“是否用客户数据训练模型”“客户数据保留多久”这类更敏感的隐私事实，也能在 KB/live source 冲突和 report claim/evidence 冲突两个阶段提前拦截。

新增测试：`backend/tests/unit/test_structured_source_claims.py` 覆盖 source-level privacy/retention 冲突；`backend/tests/unit/test_business_intel.py::test_claim_validator_detects_customer_data_training_conflict` 与 `::test_claim_validator_detects_data_retention_conflict` 覆盖 claim-level 冲突。

### 23. Activity 通知流展示 release gate metadata 摘要

## 当前主链路

```text
KB crawler / batch ingest
  -> KnowledgeRepository documents/chunks
  -> rag_retrieve_tool(mode="sparse")
  -> collector KB warm-start
  -> RawSource(candidate_origin="rag_kb")
  -> collector live verification / QA freshness / structured contradiction gate
  -> writer only uses source tokens
  -> collect_join verified sources write back to KB
  -> rollback by run_id/raw_source_id/crawl_run_id/document_id when pollution is found
  -> scoped redo affected branch from release gate blocker
```

企业证据链路：

```text
KnowledgeRepository documents
  -> enterprise kb-sync
  -> EvidenceRecord(metadata 保留 KB/collector 审计字段)
  -> enterprise search / release gate / gap fill / report source bundle
```

## 目前项目最大问题

### P0：证据可信链路仍是最大风险

虽然 KB 已接入 collector，但项目最核心风险仍然是“报告中的事实是否能完整追溯到可验证来源”。已经补了 writer token 边界、freshness gate、structured contradiction gate、KB rollback、dense 状态回查、RAG hit metadata 透传、OpenAPI 契约同步检查、release gate claim conflict 的 KB 审计 metadata，以及 run QA freshness/contradiction 证据对 metadata；这些审计信息已在前端 release gate issue 卡片和复核队列中可视化，并已接入 KB rollback 与 scoped redo 动作。后续重点应放在扩大 claim/source claim 覆盖面与更细的源快照深链。

### P0：质量门禁还偏规则化，缺少 claim 级闭环

本轮已从文本启发式升级到结构化 source claim，并让 release gate 在冲突 issue 上带出 KB document/version 与原始 collector source。后续应继续扩大结构化事实项覆盖面，把更多 writer/analyst 核心结论稳定落成 `ClaimRecord`，让“报告 claim -> source claim -> RawSource -> KB document/version”的闭环覆盖更多业务断言。

### P1：前端可解释性不足

后端已经有 KB warm-start、accepted/rejected source、freshness/contradiction issue、rollback selector 等信息；前端已展示报告 source trace 的 KB provenance、KB warm-start query、KB document/chunk id、hit/rerank score、trace 面板中的 rejected KB hit reason、Overview 的 accepted/rejected KB hit 聚合，并把 freshness/contradiction gate 指向的证据对接入报告复核和 release gate 复核队列，再连接到 Knowledge 深链。剩余缺口主要是：

1. 在 Knowledge 详情内直接定位 chunk/snippet 段落或 source snapshot artifact。
2. 更细粒度的“只 rollback 冲突 KB 文档/只重跑受影响 claim 区块”的操作联动。

### P1：重模块集中在 run service / QA / collector

`test_run_service.py` 和 agent QA/collector 逻辑仍然很重，新增测试只能缓解验收压力，不能从根上降低维护成本。后续建议继续抽离：

1. source quality/freshness/claim conflict 独立模块。
2. collector KB warm-start/write-back 独立 service。
3. run service 测试按 agent stage 拆文件。

### P1：全量 backend unit 仍未稳定验收

之前本地完整 backend unit 曾出现 exit 137。本轮已拆 CI shard，但还没有证明全量 backend unit 在本机稳定通过。后续应继续按失败/耗时拆分，并加慢测试标记。

## 结论

RAG KB 现在已经从“独立知识库/爬虫能力”推进到“collector 可复用、writer 不绕过、quality gate 可拦截、verified source 可回写、污染可回滚”的闭环雏形。

下一步最重要的是继续扩大报告 claim 与 source claim 的端到端一致性校验，补 Knowledge 详情内 chunk/snippet/source snapshot 原文定位，并推进 run service/collector/QA 重模块拆分。
