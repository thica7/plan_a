# RAG KB / Release Gate 更新（2026-06-21）

## 本轮完成

### 1. Release gate 的 `Scoped redo` 现在真的按 issue 定向执行

之前 workbench 里点击某个 release gate issue 的 `Scoped redo`，前端虽然知道是“哪张卡片”，但后端实际只是对整个 `run_id` 调用 `/runs/{run_id}/redo`，redo 选路仍然回到全局 QA finding 默认挑选逻辑。

这次补齐后：

1. `POST /api/runs/{run_id}/redo` 支持接收 `issue_ids`。
2. workbench 会把当前 release gate issue id 一起传给后端。
3. 后端 `request_redo -> run_scoped_redo` 会优先匹配：
   - 真实 `QCIssue.id`
   - `release_gate_issue_id`
   - `run_qa_finding_id`
4. 如果请求的 issue 已经失效，会直接返回 `409 Requested redo issue is no longer active.`，避免出现“点的是这张卡，重跑的是另一条分支”的失真。

这一点对验收很重要，因为它让 UI 上的操作语义和后台实际修复范围终于一致了。

### 2. Release gate issue 和运行期 QA finding 建了稳定映射

`_sync_release_gate_repair_issues` 现在会把以下信息挂到同步生成的 QA repair issue metadata 上：

- `release_gate_issue_id`
- `release_gate_gap_id`
- `release_gate_task_id`

这样后续不管是人工 redo、审计、通知流，还是更细粒度的 repair/rollback 联动，都有稳定锚点，不再只能靠 message 文本或 rule 名做模糊推断。

### 3. 前端 redo 目标也做了结构化

前端新增了 release gate redo target 推导：

- 默认带当前 `issue.id`
- 如果 issue 来源于 run-level QA，还会额外带上 `run_qa_finding_id`

这让 release gate blocker、run QA blocker、KB rollback 后的 scoped redo 三者之间的衔接更稳。

## 当前最大的剩余问题

### P0：claim 级闭环还不够细

现在已经能做到：

- release gate blocker -> QA evidence pair
- QA evidence pair -> Knowledge deep link
- Knowledge deep link -> chunk 原文 / source snapshot
- release gate blocker -> KB rollback
- release gate blocker -> issue 定向 scoped redo

但还没有做到“只重跑受影响 claim 区块”。目前 redo 仍主要按 subagent / competitor / branch 级别收口，颗粒度比以前好了，但还没有细到 claim block。

### P0：source snapshot 大文件预览仍偏基础

前一轮已经修掉了一个隐藏内存问题：source snapshot preview 不再整文件读入内存。但大 PDF / 图片目前仍以基础预览为主，还缺：

- 分页
- 缩略图
- OCR 摘要
- 更清晰的定位锚点

这会影响 reviewer 处理复杂证据时的效率。

### P1：`run_service / collector / QA` 仍然偏重

这一轮没有再回避这个问题：能力虽然在变强，但后端核心模块依然比较重，后续改动的测试与理解成本都偏高。尤其是：

- `backend/packages/orchestrator/service.py`
- `backend/tests/unit/test_run_service.py`

后面如果继续做 claim 级 redo、collector 细粒度回放、更多质量门禁规则，最好同步拆模块，不然维护压力会继续往上走。

## 建议的下一步优先级

1. 做 claim 级 redo seed，把 release gate issue 直接压缩到受影响 claim / section。
2. 让 KB rollback 支持“只回滚冲突 chunk 所在文档版本”的更细粒度路径。
3. 给 source snapshot 大文件补分页 / OCR 摘要 / 缩略图。
4. 拆分 `run_service` 中 source quality、freshness、contradiction、release gate repair 的重逻辑。
