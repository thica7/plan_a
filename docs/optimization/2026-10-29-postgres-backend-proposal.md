## 目标与当前依据

用户确认本轮重点是数据库、事务和高并发。建议新增可使用、可压测的调研提交与额度管理功能，再完善报告协作事务；保持现有 FastAPI、Agent pipeline 和 Temporal 编排方向。

本轮只读检查确认：

| 当前实现 | 需要收敛的边界 |
| --- | --- |
| `packages/enterprise/postgres.py` 已有关系型企业数据存储 | `_connect` 每次调用驱动创建同步连接，目前没有连接池；新异步接口应有独立、有限的异步连接池。 |
| 运行状态和执行协调使用 SQLite／同机文件锁 | 上轮验收范围是同机多进程，不能据此宣称 PostgreSQL 已接管完整运行状态或支持跨主机执行。 |
| `RunService.create_run` 先检查额度，随后另行创建运行并写入企业库 | 检查与占用不在一笔数据库事务中，需要防止并发请求同时看到剩余额度。 |
| PostgreSQL 报告编号通过 `MAX(version_number)+1` 查询，稍后保存报告 | 现有唯一约束可以阻止重复编号写入，但编号分配与保存分离，仍可能发生并发冲突；应提供原子分配及明确冲突返回。 |
| 企业迁移脚本包含 `CREATE EXTENSION vector` | 本机 PostgreSQL 15.18 原生工具可用，尚无 pgvector 控制文件。关系型新模块的验收需要与向量扩展依赖分开。 |

这里是源码审查结论及并发风险识别，尚未声称本轮已经复现额度超占或版本冲突。

## 方案选择

| 方案 | 取舍 |
| --- | --- |
| PostgreSQL 负责业务事务与 Outbox，复用既有执行入口及 Temporal（推荐） | 新功能落到明确业务数据，继续使用现有编排；需要解决事务边界、派发重试和运行绑定。 |
| PostgreSQL 业务库加 Redis 消费队列 | 可以独立控制队列，但要新增消费者恢复、重试和持久派发协议，并与已有 Temporal 分工。 |
| PostgreSQL 直接承担全部长任务调度 | 外部依赖较少，但需自行实现整个执行状态机、恢复和调度策略；本期不选。 |

推荐方案中的 Outbox 是“与业务记录同事务保存的待派发事件”。Relay 只负责将事件交给已有执行入口，不重新实现 Agent 调度引擎。数据库领取可以使用 `FOR UPDATE SKIP LOCKED`；它适用于队列消费者，不能用来忽略额度检查中的冲突。参见 [PostgreSQL 15 SELECT](https://www.postgresql.org/docs/15/sql-select.html#SQL-FOR-UPDATE-SHARE)。

## 第一期 持久化调研提交中心与额度账本

### 用户可以执行的操作

1. 提交调研，立即得到持久化的提交单 ID；服务重启后仍能查询。
2. 按工作区、状态和时间分页查询提交历史，查看派发状态及关联的运行 ID。
3. 在尚未派发时取消提交，额度只释放一次。
4. 对派发失败项显式重试，保留原业务身份和历史尝试记录。
5. 查看工作区本周期额度、预占记录和释放流水。

建议新增接口：

| 接口 | 作用 |
| --- | --- |
| `POST /api/task-submissions` | 带幂等键提交，事务成功后返回 202 和提交单；幂等重放返回同一提交单。 |
| `GET /api/task-submissions` | 工作区范围内的游标分页与状态筛选。 |
| `GET /api/task-submissions/{id}` | 查询提交单、派发尝试及关联 run；越工作区访问拒绝。 |
| `POST /api/task-submissions/{id}/cancel` | 仅取消尚未派发的提交；与领取派发的竞态通过数据库状态条件处理。 |
| `POST /api/task-submissions/{id}/retry-dispatch` | 显式重试允许重试的派发失败，不创建新的业务任务或重复占用次数。 |
| `GET /api/workspaces/{id}/quota-ledger` | 查看周期额度和流水，支持分页。 |

这是一组候选新增接口。现有 `POST /api/runs`、直接工作流启动、定时扫描和监控的实际任务创建也须接入同一个事务准入服务，保留各自已公布的响应合同；不能从旧入口绕过额度。派发器携带经服务端校验的预占身份，既有执行入口验证后沿用它，不二次扣额；客户端不能用请求字段自行声明已经预占。

### 事务与数据职责

建议新增提交单、幂等记录、周期额度桶、不可变额度流水、Outbox 和派发尝试记录。表名、迁移文件及最终 DTO 在批准后写入实施计划。

一次提交只使用一条数据库连接、一个短事务：

1. 校验服务端身份与工作区／项目权限。
2. 以工作区和幂等键定位请求；相同业务内容返回原结果，不同内容返回 409。
3. 原子检查并预占本周期任务次数。
4. 写入提交单、额度流水、审计和 Outbox。
5. 全部提交；任何一步失败全部回滚。

第一期额度单位为任务次数。已执行模型请求的 token／费用预算继续由现有预算模块管理，不把任务次数账本写成真实模型账单。周期使用明确的 UTC 边界，取消和重试沿用原预占周期；未派发取消可释放，已经派发或结果未知的请求不盲目返还。

幂等依赖工作区范围的唯一约束和规范化请求摘要；原子冲突处理遵循 [PostgreSQL INSERT / ON CONFLICT](https://www.postgresql.org/docs/15/sql-insert.html)。新请求的额度判断以数据库事务为准，缓存不能作为余额真值。旧入口的重放也应先识别原预占，避免因余额已耗尽而拒绝同一请求的幂等查询；迁移到新口径时要处理本周期已有任务，不能重置为零。

### 派发与已有流水线衔接

- Relay 在短事务中领取 Outbox，提交后再调用既有 LangGraph／Temporal 入口，网络和模型调用不占数据库事务。
- 固定提交单到运行／workflow 的幂等身份；发送成功但确认丢失时，重试仍查找同一个运行，不能产生第二个业务任务。
- 派发按至少一次处理，状态更新校验当前尝试身份；未知结果先核对运行绑定。不能承诺外部模型调用 exactly-once。
- 限定重试次数，保存脱敏错误、下一次重试时间及人工重试记录。
- 提交状态由 PostgreSQL 管理；现有执行状态和图检查点仍有各自存储。DTO 分别显示提交／派发状态与关联运行状态，不能混成一个强一致状态。
- 完整运行日志、图检查点和执行协调迁移属于后续独立里程碑。第一期仍按现有同机执行边界验收。

### 数据库底座

- 新模块使用 Psycopg 异步连接池，明确最大连接数、最大等待者、获取超时和应用启动／关闭生命周期；池耗尽给出可辨识的服务繁忙响应。
- 现有企业适配器的同步路径使用有界同步池，接入异步主链时采用受控执行方式；新路径不能旁路池无限创建连接。两种池均纳入总连接预算，旧模块逐步异步化。
- 为 API 和派发进程计算连接总预算，记录池等待时间、在用连接及超时。参见 [Psycopg 连接池文档](https://www.psycopg.org/psycopg3/docs/advanced/pool.html)。
- 用版本化、可核验的追加迁移管理新表，明确唯一约束、外键、合法状态与非负余额约束，不在每个请求中执行 DDL。
- 新关系型模块的迁移独立于向量扩展；不修改旧迁移的历史含义。现有完整企业适配器依赖的 pgvector 另按部署组合验收。
- 使用工作区＋创建时间＋ID 的复合索引与稳定游标；实际生成数据后记录 `EXPLAIN (ANALYZE, BUFFERS)`，避免只断言存在索引。
- 复用已有身份／RBAC；数据库连接不得携带上一个工作区的上下文。涉及 RLS 的验收使用非超级用户，不能用超级用户测试结果声称隔离有效。

## 第二期 报告协作与版本事务

新增或完善多人改稿冲突提示、版本历史分页、发布审计和通知派发：

- 以报告系列为单位，在保存新版本的同一事务内原子分配编号，保留现有唯一约束。
- 编辑／审批／发布携带预期 revision；过期修改返回 409，不覆盖其他人的提交。
- 报告保存、版本头指针、审计及通知 Outbox 同事务提交。
- 复用既有内容质量与发布审核，不因数据库改造绕过引用或内容门禁。

这期单独制定实施计划，避免同时改动任务提交和报告生命周期两套事务。

## 验收标准

第一期使用真实 PostgreSQL 多连接和真实 HTTP 服务，保留模型内部的受控响应以隔离模型配额：

1. 剩余额度 1，100 个不同请求并发提交，恰好 1 次预占成功，其余没有半成品提交单或孤立扣额。
2. 同一工作区 100 个相同幂等请求，仅有一份提交单、一次预占和一条初始派发事件；同键不同内容明确冲突。
3. 在额度、提交单、Outbox 写入之间分别注入异常，检查事务完全回滚。
4. 在外部接受任务后、Relay 写回前结束自己的进程，恢复后仍绑定原运行，不产生第二份业务任务。
5. 取消和派发并发竞争，只有合法状态转换成功，不双重释放；跨周期操作回到原额度桶。
6. 工作区隔离及连接复用后上下文隔离通过；数据库断连、锁等待和连接池耗尽均有明确结果。
7. 通过真实 socket HTTP 记录不同并发梯度下的吞吐、P50／P95／P99、失败分布、SQL／连接等待及资源占用。并发正确性目标与吞吐实测分开，不预先声称固定 QPS。
8. 从旧创建、直接 workflow、定时／监控入口提交也消耗同一份额度；伪造预占身份被拒绝，派发器合法重放不重复扣额。

本机已检查到 PostgreSQL 15.18 的 `postgres`、`initdb`、`pg_ctl`；可在批准实施后使用专属临时实例验证关系事务。部署侧 PostgreSQL 17、真实 Temporal／Redis 与 Docker 组合另在部署电脑验收。旧实例、现用数据库和真实模型账单不作为故障注入对象。
